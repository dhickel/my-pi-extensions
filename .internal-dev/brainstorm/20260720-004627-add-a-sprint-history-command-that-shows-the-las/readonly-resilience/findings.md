## Prompt

Add a `/sprint history` command that shows the last 5 completed sprint runs with their directive summary, completion timestamp, and artifact count. Read-only, no mutations.

## Findings

### 1. Data sources for history records

Three artifact kinds can exist under `.internal-dev/sprints/`:

| Kind | How completion manifests | Key evidence files |
|---|---|---|
| **planning** (completed) | `.state.json` removed after publish; `manifest.md` persists with `## Directive`, `## Artifacts`, `## Outcome`. | `manifest.md` (human-readable), optional `planning/` directory |
| **execution-only** | `execution/record.json` has `state: "completed"`, `completedAt`, `completion.report`. Companion `manifest.md` is a rendered copy. | `execution/record.json` (authoritative), `manifest.md` (rendered) |
| **ambiguous / malformed / unknown** | Should be skipped or reported as degraded, never crashed on. | Potentially nothing parseable |

**Planning-run completion timestamp**: The engine, on successful publish, calls `artifacts.removeRuntimeFiles()` which deletes `.state.json` and `.sessions/`. The `manifest.md` `## Outcome` heading typically contains a line like `Completed at 2025-07-18T12:34:56.789Z.` or similar free-form text. There is no machine-readable `completedAt` field left on disk for planning runs after cleanup. However, the `manifest.md` is written before cleanup, and its file mtime is a proxy — but mtime is filesystem-level, not logically authoritative, and can be touched by `git checkout`, `rsync`, or other operations.

**Execution-run completion timestamp**: `execution/record.json` carries `completedAt` (ISO 8601) — this is authoritative and structurally validated.

**Directive summary**:
- Planning runs: `manifest.md` `## Directive` section is free-form text. The first meaningful line after the heading is the directive summary. Sometimes it's markdown prose linking a source plan.
- Execution runs: `manifest.md` `## Directive` section is auto-generated by `renderManifest()` as ``Source plan `...` is authoritative. Planning was performed externally...`` — this is a generated stub, not a human directive. The real directive lives in the source planning run's `manifest.md` (or `input.md`).

**Artifact count**:
- Planning runs: entries under `## Artifacts` in `manifest.md` list `- \`path\` — sha256 \`...\`, N bytes`. Count these list items.
- Execution runs: same format in `manifest.md`; also available as `source.files.length` in `record.json`.

### 2. Path and symlink safety

The existing infrastructure is battle-tested:

- `sprintsRoot()` validates that `.internal-dev/sprints/` is a regular directory (no symlinks).
- `assertSafeRelativePath()` blocks traversals, control characters, absolute paths.
- `resolveRunDirectory()` + `assertValidRunDirectory()` enforce one-path-segment direct children.
- `discoverSprintRuns()` uses `readdir` + `lstat` only — never follows symlinks (every `lstat` result is checked for `.isSymbolicLink()`).
- `inspectPlanDirectory()` (in validation) performs per-component symlink rejection with `O_NOFOLLOW` on open.

**History must follow the same discipline**:
- Use `sprintsRoot()` once to resolve the store.
- Use `readdir` + `lstat` for enumeration, rejecting symlinks and non-directories.
- Read-only `readFile` on `manifest.md` and `execution/record.json` with `O_NOFOLLOW`.
- Never call `mkdir`, `writeFile`, `unlink`, `rm`, or `rename`.

### 3. Malformed or ambiguous records

`classifyRun()` already categorizes each directory as `planning`, `execution-only`, `ambiguous`, `malformed`, or `unknown`. History must handle all cases:

- **planning without manifest**: `.state.json` absent, no `manifest.md` — no data to show. Skip silently or report as degraded.
- **manifest with missing headings**: The `## Directive` or `## Artifacts` headings could be absent from a corrupted manifest. Report the run as degraded rather than crashing.
- **execution-only with malformed `record.json`**: `parseExecutionRecord` throws on structural violations. Catch, log a degraded entry, continue.
- **ambiguous (both planning and execution markers)**: Skip with a warning; can't determine which data source is authoritative.
- **active/blocked/interrupted execution records**: Filter out — only `state === "completed"` qualifies.

### 4. Missing metadata and graceful degradation

| Missing piece | Degradation strategy |
|---|---|
| No `manifest.md` for a planning run | Can't show directive or artifact count. Skip or list with "unknown" fields. |
| `manifest.md` exists but `## Directive` heading absent | Directive summary = `"(not recorded)"`. |
| `manifest.md` exists but `## Artifacts` heading absent | Artifact count = `0` or `"(unknown)"`. |
| `manifest.md` exists but `## Outcome` has no "Completed at" line | Fall back to `manifest.md` file mtime as a best-effort timestamp, annotated as approximate. |
| `execution/record.json` is valid but `manifest.md` is missing/corrupt | Use `record.json` directly for `completedAt`; directive is the source plan path (not a true directive summary). |
| Concurrent deletion (entry disappears between `readdir` and `readFile`) | Catch `ENOENT`, skip the entry, continue. |
| Permission denied on a subdirectory | Catch `EACCES`/`EPERM`, skip with a warning, continue. |

### 5. Active leases and concurrent changes

The history command **must never touch leases**. Key risks:

- **Lease inspection is read-only** via `inspectLease()` — it reads and parses `.lease.json`, classifies ownership, and returns. It does not acquire, release, or modify. History can call this safely for diagnostics only.
- **Concurrent `/sprint reset`** during history enumeration: a run's directory may be `rm -rf`'d between `readdir` and our `lstat`/`readFile`. Each step must tolerate `ENOENT`.
- **Concurrent checkpoint writes**: An active execution record's `record.json` could be partially written if the writer doesn't use atomic rename (the current code uses `atomicWriteFile` which does a temp+rename, so partial reads should not happen — but `EIO` or `EBUSY` should still be caught).
- **Lease file appearing/disappearing**: Not relevant since history doesn't touch leases. It may optionally report lease ownership for context but must never clear or take over a lease.

**Proof of no mutation**: The history function must import only `readFile`, `readdir`, `lstat` (or `stat`), and pure parsing functions from the existing modules. It must not import `acquireLease`, `releaseLease`, `writeFile`, `mkdir`, `unlink`, `rm`, `atomicWriteFile`, `publishDirectoryExclusively`, `checkpointExecutionRecord`, `finishExecutionRecord`, or any write-bearing function. A reviewer should be able to grep the function body for mutation verbs and find none.

### 6. Deterministic sorting

The prompt says "last 5 completed sprint runs." Determinism requires a stable, unique sort key:

- **Primary key**: Completion timestamp (newest first). Two sources:
  - Execution records: `record.completedAt` (ISO 8601, structurally validated).
  - Planning runs: Parse "Completed at <ISO>" from `manifest.md` `## Outcome` section. If unparseable, fall back to `manifest.md` `mtimeMs` (from `lstat`).
- **Tiebreaker**: `runId` (lexicographic). Run IDs are unique time-based slugs, so this is deterministic.
- **Filter**: Only runs with a confirmed completed status. This means:
  - Planning: `manifest.md` exists AND `.state.json` absent (or `.state.json` with `status: "completed"`).
  - Execution: `record.state === "completed"` in `record.json`.
- **Active/paused/interrupted/blocked**: Always excluded, never listed.

### 7. Command surface and UX

Integrate into the existing `/sprint` command dispatch in `handleSprint`:

```
/sprint history
```

- Parsed as a management action via `parseCommand("sprint", "history")`. The `parseCommand` function currently only accepts `status|cancel|pause|resume|reset|list|doctor`. Adding `history` requires a one-line change to the management action list.
- After parsing, history has its own handler branch in `handleSprint`.
- Output is a `ctx.ui.notify(...)` call with a multiline info-level message listing up to 5 runs, newest first.

### 8. Implementation scope boundaries

What history does **not** do:
- Does not read `.state.json` for planning runs (it's gone after completion anyway).
- Does not traverse `planning/` directories or validate their contents.
- Does not inspect execution records beyond `manifest.md` unless `manifest.md` is absent (fallback to `record.json`).
- Does not sort by anything other than completion time + run ID.
- Does not paginate beyond 5 entries.
- Does not support `--all`, `--kind`, or filtering flags.
- Does not touch, release, create, or repair leases.
- Does not run `doctor` or `validate`.
- Does not resume or bind any run.

### 9. Testability

History is a pure read-only function from a filesystem root to a structured list of `HistoryEntry` records. It can be tested with:

- A temporary sprints directory with hand-crafted `manifest.md` and `execution/record.json` fixtures.
- Edge cases: empty store, 0–6 completed runs, mixed planning/execution/ambiguous/malformed directories, manifests with missing headings, execution records with `state: "active"` (filtered out), concurrent deletion simulation, permission error simulation.

## Options

### Option A: Single-function approach (`discoverHistory`)

Add a new exported function `discoverHistory(sprintsRoot: string): Promise<HistoryEntry[]>` in `run-records.ts` that reads manifests and execution records, filters to completed, sorts by timestamp, and returns the top 5. Then add a `/sprint history` handler branch in `index.ts` that calls it and renders results via `ctx.ui.notify`.

**Pros**: Minimal new surface area, reuses existing `sprintsRoot`, `resolveRunDirectory`, `classifyRun` infrastructure. Easy to test in isolation.
**Cons**: Adds another discovery function alongside `discoverSprintRuns`. May duplicate some classification logic.

### Option B: Extend `discoverSprintRuns` with history-specific metadata

Add optional `includeHistory?: boolean` to `discoverSprintRuns` that, when set, also reads manifestation data (directive, timestamps, artifact counts) into each `RunRecordSummary`. Then filter/sort/limit in the command handler.

**Pros**: Avoids a separate discovery pass; richer `RunRecordSummary`.
**Cons**: Changes the `RunRecordSummary` type (a breaking API change unless new fields are optional). Adds read I/O to what is currently a lightweight directory scan. Mixes lightweight listing with heavy content reading.

### Option C: Command-handler-only inline logic

Write the entire history logic inside `handleSprint` as a private helper function, not exported. Import only what's needed for reading manifests and execution records.

**Pros**: Simplest scope change; no exported API surface. Keeps history as a UX feature only.
**Cons**: Not reusable by other tools or tests except through command invocation. Harder to unit test in isolation.

### Recommended: Option A

A clean exported function with a well-defined return type, tested independently, and called from a thin command handler in `index.ts`. This follows the pattern already established by `discoverSprintRuns` and `runDoctor`.

## Trade-offs

### Manifest mtime as fallback timestamp

For planning runs where the `## Outcome` section has no parseable ISO timestamp, using `manifest.md` mtime is pragmatic but imprecise. `git checkout` or file synchronization can reset mtime, causing ordering instability. The alternative (excluding runs without parseable timestamps) would silently drop entries, which is worse UX. Mitigation: annotate mtime-derived timestamps with `(approx.)` in the output.

### Execution records' directive is a stub

`renderManifest()` generates `## Directive` as a reference to the source plan path, not the original planning directive. For a truly useful history, we'd need to walk from the execution run back to its source planning run (via `source.sourcePlanningRunId`) and read that planning run's `manifest.md` `## Directive`. This introduces a dependency chain: if the source planning run was reset, the directive is lost. For V1, showing the source plan path is acceptable.

### Filtering by "completed"

For planning runs, there's no definitive machine-readable `completed` flag on disk after cleanup — we infer completion from `manifest.md` existence + `.state.json` absence. This could false-positive if a run's `.state.json` was manually deleted but the run never actually completed. The existing `/sprint list` and `/sprint doctor` have the same inference. It's an acceptable heuristic.

### Sorting determinism under timestamp collision

Two runs could share the same completion timestamp if they were completed in rapid succession (same second). The `runId` tiebreaker (lexicographic) ensures deterministic but arbitrary ordering in that case. Run IDs embed a time-based prefix, so chronologically-adjacent runs will sort naturally even on collision.

## Open Questions

1. **Should history include execution-only runs, planning runs, or both?** The prompt says "sprint runs" generically. The `/sprint` workflow creates planning runs; `sprint_execution_record start` creates execution runs. Both live under `.internal-dev/sprints/`. I recommend including both, with a `kind` label in each output line (e.g., `(planning)` vs `(execution)`).

2. **How should the directive summary be rendered for execution runs?** The execution manifest's `## Directive` is a machine-generated stub. Options: (a) show the source plan path, (b) cross-reference the source planning run's directive if the planning run still exists, or (c) mark it as `"(execution record)"`. I recommend (a) for V1, with (b) as a follow-up enhancement.

3. **Should history respect the Pi session binding (`bound`)?** The existing `/sprint status`, `/sprint list`, and `/sprint doctor` commands all work on the global `.internal-dev/sprints/` store, not just the currently bound sprint. History should follow the same pattern — show the last 5 completed across all runs in the store, independent of session binding.

4. **What format should the output take?** The existing `/sprint list` uses a compact `runId  kind  state  markers=...  lease=...` format. History could use a similar tabular format with columns for timestamp, directive summary (truncated), kind, and artifact count. Or it could be richer multiline output. For V1, compact single-line-per-run with timestamp prefix is consistent with the existing convention.

5. **Timeout or concurrency limit on reading many manifests?** If the store has hundreds of runs, reading every manifest to find completed ones could be slow. For V1 with a cap of 5 output entries, we can sort directory names by recency (they embed timestamps) and read manifests in order until we find 5 completed runs, with a reasonable stop threshold (e.g., check at most 30 directories).

## Recommended Next Step

Proceed with **Option A**: implement `discoverHistory()` as a new exported function in `run-records.ts` (or a new `history.ts` module) with these design decisions:

1. **Include both planning and execution runs**, labeled by kind.
2. **For planning runs**: read `manifest.md`, extract directive from `## Directive` section, count artifacts from `## Artifacts` list items, parse `## Outcome` for completion timestamp with `manifest.md` mtime fallback (annotated).
3. **For execution runs**: read `manifest.md` first; if absent or malformed, fall back to `execution/record.json`. Use `completedAt` for timestamp. Show source plan path as directive summary.
4. **Filter strictly to completed**: planning runs need `manifest.md` present + no `.state.json`; execution runs need `record.state === "completed"`.
5. **Sort by timestamp descending, tiebreak by runId ascending; take top 5**.
6. **Tolerate all read errors**: ENOENT, EACCES, malformed JSON, missing headings — skip the entry or annotate as degraded, never throw.
7. **Zero mutations**: import only read functions. No write, no lease, no repair.
8. **Add `"history"` to `parseCommand`'s management action list** and a handler branch in `handleSprint`.
9. **Write unit tests** using temporary filesystem fixtures covering: empty store, mixed kinds, various completion states, malformed manifests, missing headings, concurrent deletion, and deterministic ordering.
